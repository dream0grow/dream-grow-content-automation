## 1. 벤치마킹에서 배운 것 (X·유튜브·문서 리서치 요약)

이 원격 세션은 네트워크 정책상 X·유튜브·개인 블로그 직접 접속이 차단되어,
웹 검색(요약 포함)과 Claude Code 공식 문서를 근거로 정리했다.
(사용자가 브라우저로 직접 수집하는 절차는 2장 참고.)

### 자주 반복되는 7가지 패턴

1. **한 에이전트 = 한 책임.** 목표·입력·출력·인계 규칙을 하나씩만 준다.
   "리서처·작가·비평가·퍼블리셔"처럼 역할을 쪼갠 파이프라인이 정석.
2. **뉴스룸 구조.** X 스레드 자동 생산 사례에서 검증된 구조:
   초안 → 팩트체크 → 에디터 교정 → 폴리시(브랜드 보이스) → 발행,
   각 단계 사이에 자동 피드백 루프.
3. **검증자(Verifier)는 반드시 새 컨텍스트로.** 같은 모델이라도
   "만든 에이전트"와 다른 fresh context에서 검토하면 오류를 훨씬 잘 잡는다.
   자기가 쓴 글을 자기가 검사하면 만든 편향을 그대로 물려받는다.
4. **병렬은 명시해야 돈다.** "서브에이전트 3개로 병렬로" 하고 콕 집어야
   fan-out이 일어난다. 병렬 N개 = 비용 N배이므로 싼 모델(Haiku급)로
   기계적 작업을 돌리고, 판단이 필요한 단계만 상위 모델을 쓴다.
5. **요약만 돌려받기.** 서브에이전트의 결과는 "요약 한 단락"으로 받아야
   메인 컨텍스트가 안 터진다. 원문 전체를 돌려받는 설계는 안티패턴.
6. **description이 곧 라우팅.** `.claude/agents/*.md`의 description을
   "언제 이 에이전트에 위임해야 하는가" 관점으로 행동 지향으로 쓴다.
7. **판정단(Judge panel) 선발.** 같은 주제로 독립 초안 N개를 병렬 생성
   → 심사 에이전트가 채점 → 1등을 뽑고 2등의 좋은 부분을 접붙인다.
   한 개 초안을 반복 수정하는 것보다 품질 상한이 높다.

## 2. 초보자용: X·유튜브 벤치마킹 따라하기 (브라우저 수집 루틴)

Claude 원격 세션은 X·유튜브에 직접 못 들어가므로, **수집은 사람이 브라우저에서,
분석·정리는 Claude가** 맡는 분업이 현실적이다. 주 1회 30분이면 된다.

### 2-1. X(트위터) 수집 — 10분

1. X 검색창에 아래 검색어를 넣는다 (그대로 복사).
   - `claude code subagents min_faves:200` — 좋아요 200+ 인기글만
   - `"sub agent" content pipeline min_faves:100`
   - `claude agents workflow filter:links min_faves:100` — 링크 있는 글
   - 한국어: `클로드 코드 서브에이전트`, `AI 에이전트 자동화 후기`
2. 정렬을 "인기순(Top)"으로 두고, 스레드를 연 뒤 **전체 글을 드래그 복사**한다.
   이미지 속 다이어그램은 스크린샷.
3. 좋은 계정을 발견하면 팔로우 대신 **리스트**("AI agents" 리스트)에 담는다.
   다음 주부터는 리스트 타임라인만 훑으면 된다.
4. 복사한 글을 볼트 `data/agent_benchmark/inbox/`에
   `YYYY-MM-DD_출처_한줄요약.md`로 붙여넣는다 (스크린샷은 같은 폴더).

### 2-2. 유튜브 수집 — 10분

1. 검색어: `claude code subagents tutorial`, `AI content pipeline automation`,
   `claude code 서브에이전트` — 필터를 "이번 달·조회수순"으로.
2. 영상은 다 볼 필요 없다. **더보기 → 스크립트(자막) 표시 → 전체 복사**.
   (자막 버튼이 없으면 영상 설명란 + 고정 댓글만 복사해도 충분하다.)
3. 같은 폴더에 `YYYY-MM-DD_yt_영상제목.md`로 저장. 링크도 함께.

### 2-3. Claude에게 분석 맡기기 — 10분

세션에서 이렇게 요청한다:

> "data/agent_benchmark/inbox의 새 파일을 읽고,
> ① 우리 파이프라인에 없는 기법 ② 이미 있는 기법 ③ 적용 제안 3개를
> data/agent_benchmark.md에 누적 정리해줘. 처리한 파일은 archive/로 옮겨줘."

이건 이미 있는 `cardnews_benchmark.py`(카드뉴스 벤치마킹 → `data/cardnews_benchmark.md`
→ 생성 시 프롬프트 주입)와 같은 구조다. 쌓인 `data/agent_benchmark.md`는
나중에 에이전트 개선 세션의 재료가 된다. 익숙해지면 이 분석 단계를
`self_improve.py`(주간 회고)에 배선해 자동화할 수 있다.

**요령**: 수집할 때 "우리 문제"를 검색어에 넣어라. "subagents"만 찾으면 일반론만
나온다. "approval bottleneck automation", "AI content human review reduce" 처럼
지금 막힌 지점을 검색하면 바로 쓸 수 있는 글이 걸린다.

## 3. 현재 파이프라인 진단

### 실측 (2026-08-26, vault/파이프라인/활성 62건)

| 상태 | 건수 | 의미 |
|---|---|---|
| approval / needs_human | **44** | **발행 승인 대기 — 병목** |
| analysis / needs_human | 7 | 분석 단계 사람 대기 |
| draft / needs_human | 5 | 유튜브 원고 등 (설계상 촬영 종착) |
| research / queued | 3 | 자동 진행 중 |
| published / done | 3 | 발행 완료 |

### 장점 (이미 잘 갖춘 것)

- **벤치마킹 7패턴 중 5개를 이미 구현**하고 있다:
  단계별 역할 분리(리서치→키워드→브리프→초안), 작가↔비평가↔검수 토론 루프
  (뉴스룸 구조), HUMANIZE_RULES 주입(폴리시 단계), 루브릭 평가+점수 미달 시
  재작성, 승인 게이트. 웬만한 벤치마킹 사례보다 구조가 앞서 있다.
- **사람 개입 최소화 설계**: 키워드 자동승인, 매일 자동 발제, 텔레그램 핑퐁,
  발행 예약(21:00). 사람 액션은 이론상 "발행 승인 1탭"뿐.
- **학습 루프 존재**: `style_learn.py`가 AI 원본 vs 사람 수정본 diff를
  Honcho에 학습 — "수정 안 해도 되는 품질"로 수렴할 기반이 이미 있다.
- **멀티포맷 출구**: 스레드·뉴스레터·카드뉴스·유튜브 롱폼·릴스·썸네일·쇼츠까지
  형식 커버리지가 넓다.

### 단점 (생산량을 막는 것)

1. **승인 적체 = 발행 0에 수렴.** 하루 1건 발제인데 승인은 그보다 느려서
   대기 44건. 만들수록 쌓이기만 한다. 카드가 쌓이면 사람은 더 안 열어본다
   (심리적 부채). → 생산량(업로드 수)은 생성 속도가 아니라 **승인 속도**가 결정.
2. **승인에 근거가 없다.** 알림은 "초안 완성"만 알려주고, 사람이 전문을 읽고
   판단해야 한다. 검증 점수·위험 요약이 없으니 승인 1건의 비용이 크다.
3. **수정률을 측정하지 않는다.** style_learn이 diff를 학습에는 쓰지만
   "이번 달 사람 수정률 몇 %"라는 KPI로 집계하지 않는다. 품질이 좋아지는지
   나빠지는지 숫자가 없어 자동승인 범위를 넓힐 근거를 못 만든다.
4. **비평가가 같은 컨텍스트 안에 있다.** agent_dialogue의 작가·비평가·검수는
   한 파이썬 프로세스의 프롬프트 교대라, 벤치마킹의 "fresh context 검증자"
   효과(만든 편향과 분리)가 약하다.
5. **1키워드 1초안.** 판정단 패턴(3안 병렬 → 선발)이 없어 품질 상한이
   "첫 초안 + 수정 2라운드"에 묶인다.
6. **재활용(리퍼포징) 미배선.** 발행된 스레드를 카드뉴스·릴스로 변환하는 건
   각각 수동 트리거다. 같은 원고에서 파일 수를 2~3배 뽑을 수 있는데 안 뽑는다.

## 4. 생산량을 늘리는 제안 (우선순위순)

### P1. 발행 심사관 서브에이전트 — 승인을 "읽기"에서 "결재"로 (효과 최대)

새 단계 `verify`를 초안 완성과 승인 요청 사이에 넣는다.
**초안을 만든 대화와 분리된 fresh context**에서 별도 LLM 호출로:

- 루브릭 점수(기존 rubric_review 재사용) + AI 티 잔존 검사(HUMANIZE 기준)
- 사실·수치 위험 문장 목록 (외부 근거 대조)
- 브랜드 보이스 일치도
- **종합 판정: `자동발행 추천` / `조건부(수정 1곳)` / `사람 확인 필요`**

텔레그램 알림이 "초안 완성"이 아니라
"✅ 심사 통과(47/50) — 위험 0건 — 승인 추천. 훅: (첫 문장)"으로 바뀐다.
사람은 전문을 안 읽고도 결재할 수 있다. → **승인 1건당 시간 5분 → 30초.**

### P2. 승인 다이제스트 + 일괄 승인 — 적체 44건 해소

- 하루 1회 텔레그램 다이제스트: 대기 카드 목록(ID·훅 문장·심사 점수).
- 답장 "1,3,5 승인"을 script_feedback이 파싱해 일괄 `approval_status: approved`.
- 기존 44건은 P1 심사관을 소급 실행해 "추천 상위 10건"부터 밀어내기 시작.

### P3. 수정률 KPI — 자동승인의 근거 만들기

- 발행 시 style_learn diff에서 **편집거리 비율**(사람이 바꾼 글자 수 ÷ 전체)을
  카드 frontmatter와 월간 리포트(`_system/logs/quality_kpi.md`)에 기록.
- 목표 예: "스레드 포맷 수정률 3% 미만 4주 연속 → 심사 통과 카드는
  `DG_AUTO_APPROVE_PUBLISH=thread`로 자동발행" — 신뢰를 숫자로 쌓아
  포맷별로 단계적 완전 자동화.
- 이게 사용자가 정의한 "퀄리티 = 사람이 수정을 거의 안 해도 됨"의 직접 측정.

### P4. 3안 병렬 + 판정단 — 품질 상한 올리기

- 초안 단계에서 훅 유형이 다른 3안을 병렬 생성(작가 프롬프트에 변주 지시,
  기계적 라운드는 저비용 모델) → 심사 에이전트가 채점·선발, 2등의 좋은 훅 접붙임.
- 벤치마킹 데이터(`benchmark_posts.md` 12훅)와 결합하면 훅 A/B 실험도 된다.
- 비용이 늘므로 P3 KPI로 "3안이 수정률을 실제로 낮추는지" 확인 후 유지 결정.

### P5. 리퍼포징 팬아웃 — 파일 수 2~3배

- 발행 완료(`stage: published`) 스레드 카드를 감지해 자동으로
  카드뉴스 PNG + 릴스 초벌 MP4 생성 → `05 리뷰/대기`에 넣고 알림.
- 이미 있는 cardnews.py·reels_video.py를 cron에서 잇기만 하면 된다.
  글 1건 승인 = 업로드 가능 파일 3건.

### P6. 벤치마킹 상시화

- 2장의 수집 루틴을 주 1회 습관으로. 분석은 `self-improve.yml` 주간 회고에
  "agent_benchmark/inbox 소화" 단계로 배선 → 개선 제안이 큐시트로 나온다.

### 예상 효과

| 지표 | 현재 | P1+P2 후 | P3~P5 후 |
|---|---|---|---|
| 주간 발행(업로드 파일) | ~1건 | 5~7건 (적체 해소) | 10건+ (리퍼포징 포함) |
| 승인 1건 소요 | 전문 읽기 (수 분) | 결재 30초 | 상당수 0초 (자동) |
| 사람 수정률 | 미측정 | 측정 시작 | 포맷별 <5% 목표 |

### 실행 순서 제안

1. **1주차**: P1 심사관 + P2 다이제스트 구현, 기존 44건 소급 심사 → 적체 해소 시작
2. **2주차**: P3 KPI 집계 배선, P6 벤치마킹 루틴 시작
3. **3~4주차**: KPI 보고 P4 3안 판정단·P5 리퍼포징 도입, 첫 포맷 자동발행 전환 검토
