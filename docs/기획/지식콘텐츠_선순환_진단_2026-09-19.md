# 지식·콘텐츠 선순환 시스템 진단 및 정리안

작성: 2026-09-19, Aside
상태: 코드·운영 로그 점검과 설계 제안. 아래 목표 구조는 아직 구현하지 않았다.

## 1. 결론

**전면 폐기보다는 핵심 연결부를 재설계하는 점진적 전환을 권한다.**

보존할 자산은 기존 원고·관찰·수정 이력, 유튜브 리서치 웹 UI, 콘텐츠 생성·발행 어댑터, 영상 편집 엔진이다. 바꿀 대상은 Git/폴더/frontmatter를 사용자가 직접 다루는 운영 방식, 서로 다른 원고 버전·상태 모델, 지식 검색과 환류의 단절이다.

목표는 원고를 더 많이 생성하는 것이 아니라 다음 순환의 완결이다.

```text
생활·Plaud·책·논문·유튜브 수집
  → 출처와 화자가 보존된 자료
  → 내 해석·의견을 검토한 지식
  → 관련 지식·반론·실제 사례로 콘텐츠 구성
  → 동일 최종본의 사실·표현·개인정보 검수
  → 사람 승인·발행
  → 수정 과정에서 생긴 새 통찰과 관객 반응을 구분해 회수
  → 기존 지식 보완·반박·연결
```

문체 학습, 전문지식 축적, 조회수 최적화는 서로 다른 세 가지 학습이다. 지금은 첫 번째의 코드가 상대적으로 많고 두 번째가 약하다.

실제 중복·분산 지점:

1. 루트 `pipeline.py`/`main.py`/`thread_generator.py`/`diff_learner.py`와 신형 `orchestrator/`/`vault_pipeline/script_learn.py`의 제작·수정학습 경로.
2. Python `orchestrator/obsidian_state.py:195–237`와 TypeScript `yt_research/lib/pipeline.ts:63–192`가 파일명·분류·채번·카드 스키마를 따로 구현. TS 주석도 수동 일치를 요구한다.
3. `shorts/render.py`, `shorts_gpt/render.py`가 전사·구간·자막·렌더 함수를 상당 부분 병렬 유지. `tools/shorts_edit.py`는 무음·박수 기반 편집 및 다른 ASR 경로를 별도로 가진다.
4. `youtube/`는 `OWNERSHIP.md`상 10x인생 채널 소유다. 이름이 비슷하다는 이유로 그로우써클 제작 코드와 합치지 않는다.

## 5. 가장 중요한 결함과 구조적 단절

### P0. 발행·검수·지식 환류가 같은 원고 버전을 보지 않는다

- `feedback.py:108–110`은 `read_latest_section('초안 ...')`을 읽는다.
- `publish.py`와 `style_learn.py`는 `read_final_draft()`를 사용한다.
- `obsidian_state.py:302–328`은 2차안·3차 수정 등 가장 높은 차수를 최종본으로 선택한다.
- 결과: 사람이 최종 수정에서 만든 통찰이 지식 환류에서 빠지고, 이미 고친 초기 표현이 다시 메모가 될 수 있다.
- `run.py:415–449`에서는 윤리검수 결과를 정한 뒤 2차안을 만들 수 있다. `rubric_review.py:56–65`는 수정본 저장 후 재검수를 하지 않는다. 승인 게이트(`run.py:546–578`)는 원고 hash가 아닌 카드의 기존 review_status를 본다.

**조치:** 원고 revision ID/hash를 만들고 검수·승인·발행·환류가 그 버전만 참조하도록 한다. 수정하면 승인과 검수를 만료시킨다. 이미 외부 발행된 본문 snapshot은 변경 불가로 보관한다.

### P0. 인기·문장력 평가와 사실 검증이 혼재한다

- `agent_dialogue.py:122–125,160–163`의 윤리검수 입력은 주로 초안이다. 주장별 근거 원문과 인용 위치를 대조하는 별도 검증기가 아니다.
- `manus_research.py:160–170`의 fallback은 명시적으로 웹 검색 없이 모델 지식으로 리서치를 작성한다.
- `prompts.py:469–484`의 글 점수는 후킹·가독성·실천성·브랜드핏·공감 중심이다.

**조치:** 개인 관찰, 의견, 과학적/통계적 주장을 구분한다. 검증 필요한 주장은 출처 원문·위치·대상·한계와 대응시킨다. 출처 미확인 수치나 일반화는 삭제·완화하거나 보류한다. 문장력 점수가 높아도 이 게이트는 우회하지 못하게 한다.

### P1. 주력 SNS 생성이 개인 지식을 자동 활용하지 않는다

- `run.py:304–315,390–396`의 Threads/뉴스레터 생성은 카드의 리서치·키워드·글감, 문체 메모리, 정적 벤치마킹을 입력으로 사용한다. 이 경로에 승인된 개인 제텔 검색 단계가 없다.
- `daily_intake.py:31–53`도 기존 카드 제목과 발제 프롬프트 중심이다.
- 반면 yt_research는 `getVaultContext()`로 지식 검색 결과를 대본에 넣는다. 두 경로의 지식 활용 수준이 다르다.

**조치:** 모든 제작 채널이 동일한 `getEvidencePack(topic, audience)`를 사용한다. 승인한 내 주장·실제 사례·외부 근거·반론/적용 한계를 함께 반환한다. 적합한 내 지식이 없으면 일반적인 글을 양산하지 말고 하나의 구체적 질문을 보내거나 다른 소재를 선택한다.

### P1. 지식 검색은 있지만 검토 상태·저자 구분이 부족하다

`yt_research/lib/vault.ts:152–226`은 볼트 전체 Markdown에서 이름·본문·임베딩 점수를 합쳐 검색한다. 해당 검색 함수에는 candidate, AI 작성, 비공개, 노랑 사례 등을 제외하는 검증이 없다. `:241–245`는 검색 결과를 '내가 직접 쌓아온 경험·사례·관점'이라고 프롬프트에 소개한다.

**조치:** 검색 점수보다 먼저 사용 자격을 검사한다. `owner`, `speaker`, `authorship`, `review_state`, `privacy`, `source_type`을 독립 필드로 둔다. 외부 영상은 형식 벤치마크와 사실 근거를 구분하고, AI 요약을 사용자의 실제 경험으로 소개하지 않는다. 임베딩은 이미 있으므로 또 만드는 것보다 이 필터가 우선이다.

### P1. SNS 완성 원고 전체가 지식으로 돌아오지는 않는다

- `feedback.py:30–39,64–127`의 대상은 교사 초안 일부와 파이프라인 발행 카드의 Threads/뉴스레터다.
- `script_learn.py:63–81,104–146,190–230`은 SNS 확정 원고에서 문체 diff를 학습하지만 제텔 원자 메모를 만들지 않는다.
- 즉 문체를 배웠다고 지식을 축적한 것은 아니다.
- `feedback.py:174–198`은 모델 발췌를 원문과 대조하지 않고 author를 사용자로 지정한다. '원출처 추적 필요' 표시가 있지만 지식 검증과는 다르다.

**조치:** 모든 확정 콘텐츠 revision에 동일한 환류 이벤트를 발생시킨다. 새 관찰, 새 주장, 기존 생각의 수정, 적용 한계만 후보로 추출한다. 요약을 무조건 여러 메모로 복제하지 않는다. 기존 지식과 supports/contradicts/refines/applies 관계를 제안하고 사용자의 짧은 확인 후 반영한다. 자기 콘텐츠를 외부 사실 근거로 순환 인용하지 않는다.

### P1. 큐 상태의 의미와 처리 규칙이 불일치한다

- 로컬 25개 카드의 `research/queued`는 `run.py:663–674`의 `research/running` 처리 조건에 맞지 않는다. 오래된 running 복구도 brief/draft만 대상으로 한다(`:718–734`). 해당 로컬 카드들은 현재 일반 디스패치 경로에서 빠진다. 원격의 동일 카드 상태는 별도 대조해야 한다.
- 유튜브/릴스/블로그 전용 카드는 원고 제작 완료 시 `published/done`을 사용한다(`run.py:370–382`). 실제 플랫폼 발행 완료와 다르다.

**조치:** production_ready, approved, publishing, published, feedback_pending을 분리하고 유효한 전이만 허용한다. 정체 상태를 진단한 뒤 개별 재큐해야 하며 일괄 승인해서는 안 된다.

### P1. Plaud는 요약보다 출처 보존과 연결이 부족하다

- 자동 조회는 기본 최근 7일·3건 처리(`run.py:78–86`), 전사 입력은 앞 60,000자로 자른다(`:30–40`). 긴 회의 뒷부분 또는 조회 기간 밖 자료를 회수하는 별도 백필·분할이 필요하다.
- `_transcript_text()`는 segment content를 이어붙인다(`plaud_client.py:219–239`). segment별 화자·시간을 별도로 보존하지 않는다.
- `write_memos()`는 LLM 발췌에 `verbatim: true`를 붙이지만 원문 포함 여부를 검사하지 않는다(`writers.py:143–161`). 다른 회의 참석자의 말이 사용자의 생각으로 잘못 귀속되지 않게 해야 한다.
- 자동 초안 제작은 교사 글감 경로로 분기한다(`run.py:56–59`). 학부모 콘텐츠로 연결하는 공통 지식 발제 단계는 따로 필요하다.

**조치:** recording_id와 segment_id, 화자, 시간, 원문 hash를 보존한다. 긴 녹음은 분할·통합하고 누락을 보고한다. 발화, 해석, 실행 약속, 일반화된 지식 후보를 분리한다. 학생·제3자 정보는 지식화 및 외부 AI 전송 전에 최소화·익명화하고, 원문 접근권한과 보관기간을 별도로 둔다.

### P2. 팀 정의, 레거시 실행, 문체 학습이 분산돼 있다

- `.claude/agents/zk-*.md`가 존재하지만 현재 `vault-agents.yml:18–42`의 실행은 socrates 질문 작업이다. 지식팀 전체의 상주 실행을 뜻하지 않는다.
- `agents/team_runner.py:42–47`과 `scheduled/*.plist`, 루트 `pipeline.py` 등에 옛 절대경로가 남아 있다. 설치·가동 여부는 이번 점검에서 확정하지 않았다.
- `script_learn.py:224–226`은 Honcho 저장 실패도 learned에 기록하며 다음 동일 hash를 건너뛸 수 있다. `style_learn.py`의 재주입은 Honcho 기반이므로 로컬 로그만 남는 경우 다음 글에 반영되지 않을 수 있다.

**조치:** 진입점과 실제 실행자를 목록화하고, 외부 저장 실패의 재시도 상태를 별도로 둔다. 레거시는 호출·데이터 경로가 없어졌음을 확인한 다음 archive한다. diff_learner는 아직 다른 모듈에서 import하므로 즉시 삭제하지 않는다.

## 6. 권장 목표 구조

### 사용자 화면: 기존 yt_research를 확장한 개인 웹 작업실

맥북·폰·윈도우에서 같은 주소와 로그인으로 사용한다. 화면은 다음 다섯 개면 충분하다.

1. 수집함: Plaud, 영상, 링크, 짧은 일상 메모. 처리 상태와 누락 사유.
2. 지식: 내 생각, 근거, 반론, 연결, 사용한 콘텐츠. 직접 편집과 버전 기록.
3. 제작실: 지식 묶음에서 채널별 원고 생성. 원문/변경점/출처를 한 화면에 표시.
4. 검토함: 고칠 문장과 이유만 강조. 최종 승인·예약. Git 조작은 숨김.
5. 운영판: 새 지식 수, 실제 발행 수, 검토 적체, 작업 실패, 마지막 정상 수집, 비용.

Telegram은 빠른 입력·알림·간단한 승인 창구로 남기되, 긴 편집과 근거 확인은 웹으로 연결한다. Obsidian은 원하면 Markdown export를 읽는 개인 뷰어로 남긴다. Git은 코드와 내보내기 백업용이지 사용자의 작업 UI가 아니어야 한다.

### 데이터와 실행 책임

```text
웹 UI + Telegram
        ↓ 인증된 공통 API
PostgreSQL/Supabase: 지식·원고 버전·근거 관계·검토·작업 상태
Object Storage: 음성·영상·렌더 결과·허용된 원문 자료
        ↓ 작업 큐
Python worker: 수집 → 지식 후보 → 제작 → 검증 → 승인 대기 → 발행 → 환류
        ↓
Markdown export/백업 (선택적 Obsidian)
```

기존 Supabase를 확장하되 새 스키마와 접근권한을 분리한다. 새로운 벡터 DB나 범용 에이전트 프레임워크를 먼저 도입할 이유는 없다. 시작은 DB job table과 제한된 worker로 충분하다.

핵심 엔티티:

- source, source_segment: 원천과 화자·시간·인용 위치
- knowledge_note, knowledge_revision: 내 주장·상태·수정 이력
- relation: 지지, 반박, 보완, 적용, 파생 관계
- content, content_revision: 채널별 산출물과 불변 최종본
- claim_evidence, review, approval: 주장·근거와 특정 revision의 검수·승인
- publication: 플랫폼 ID, URL, 발행 본문 snapshot, 상태
- feedback: 문체 교정/지식 수정/성과 관찰을 구분
- job: 입력 revision, 재시도, lease, heartbeat, 오류와 결과

인증·접근 제어, 사용자별 권한, 최소 권한 worker, 비밀값 관리가 전제다. 과도한 동시 편집을 위해 처음부터 CRDT를 도입하기보다 revision 비교와 충돌 안내부터 구현한다.

### 24시간 운영과 Linux 노트북

- GitHub Actions는 이미 맥북과 독립적으로 실행된다. 다만 cron은 정시 실행이나 최대 지연을 보장하는 큐가 아니다. 이번 실행 목록에서도 설정된 15분 간격과 실제 시작 간격은 일치하지 않았다.
- 장기 작업은 웹 요청 처리와 분리한 상시 worker로 이동한다. 작업별 timeout, 재시도, 입력 hash, 중복 방지, 실패 큐, 마지막 정상 완료 시각을 둔다.
- 발행 직후 네트워크가 끊기면 무조건 재전송하지 않는다. 플랫폼 게시물과 대조하고 결과 불명 상태를 관리한다. 동일 콘텐츠·채널·revision은 한 번만 발행하도록 관리한다.
- 집의 Linux 노트북은 렌더·전사 worker나 백업용으로 유용하다. 처음부터 DB·유일한 원본·외부 접속 웹 서버까지 모두 집 노트북에 두지는 않는다. 전원·인터넷 장애가 전체 작업실 장애가 되기 때문이다.
- `shorts/render.py:51–65`와 `shorts_gpt/render.py:53–61`의 MLX Whisper는 Apple Silicon 경로다. Linux에서는 ASR 인터페이스를 분리하고 faster-whisper 등으로 바꿔야 한다. `tools/shorts_edit.py:266–286`에 이미 해당 경로가 있다.
- Linux의 실제 성능·전기료·배터리 상태는 하드웨어 미확인으로 판단하지 않았다. 작은 영상으로 먼저 속도를 측정한다. 덮개 닫힘 절전, 재부팅 자동 시작, 디스크/온도 감시, 암호화·백업, 안전한 원격 접속이 필요하다.
- `tools/viewtrap_cookie_sync.py`는 macOS Keychain/launchd 의존이다. 이것과 로컬 브라우저 작업은 맥북 수면 영향을 받는다. OS 이전만으로 그대로 해결되지 않는다.

## 7. 품질을 높이며 사람 병목 줄이기

사람의 전문적 판단을 없애지 말고, 저가치 반복 편집을 줄인다.

1. 사용자가 만족한 원고 10~20개와 반려·수정 사례를 기준 세트로 만든다. 후킹뿐 아니라 정확성, 관점, 실제 사례, 적용 한계, 문체를 평가한다.
2. 지식·근거 묶음이 준비된 소재만 제작한다. 검토 적체가 많으면 추가 대량 생성 대신 좋은 후보 소수만 보낸다. 운영 제한 변경은 별도 실행 시 적용한다.
3. 작가·근거 검증·표현 편집의 역할을 분리하고 라운드와 비용을 제한한다. 같은 모델끼리 동의했다는 이유로 사실을 확정하지 않는다.
4. 사용자에게 초안 전체를 매번 다시 검토시키지 않고, 변경 문장·근거 부족·승인 필요한 사례를 표시한다.
5. 사실·관점 교정을 문체 취향과 분리 저장한다. 틀린 학습 규칙은 취소 가능하게 한다.
6. 성과는 소재·표현 실험의 신호로만 사용한다. 조회수가 높다는 이유로 주장의 참됨이나 교육적 타당성을 승격하지 않는다.

권장 지표: 첫 제출 승인율, 편당 사람 수정 시간, 근거 미확인 주장 수, 개인정보 차단, 실제 발행 성공률, 발행 후 환류 완료율, 승인 지식의 재사용률, 비용/승인 원고. AI 자기평가 점수나 생성 개수는 보조 지표다.

## 8. 단계별 정리 순서와 완료 기준

### 0단계: 안전과 상태 정합성

- 미커밋 변경·이동/삭제 파일의 의도를 확인하고 코드/데이터 백업 및 기준 revision 확보.
- 최종본 읽기 통일, 검수·승인 hash 고정, 제작완료/실제발행 상태 분리.
- research/queued 정체 카드와 최근 수집 0건을 진단. 인증 오류·정상 빈 목록·파싱 실패를 분리.
- 회귀 테스트: 최종 수정본만 환류, 수정 후 승인 만료, 미확인 인용 차단, 중복 발행 방지.

완료 기준: 검수·발행·환류가 모두 동일 원고 revision을 참조하고 잘못된 상태를 자동 진단한다.

### 1단계: 작지만 완전한 선순환

Plaud 전사 1건 + 사용자가 만족한 기존 콘텐츠 10편으로 제한한다.

- 화자/원문 구간 → 지식 후보 → 사용자 확인 → 관련 지식 연결.
- 그 지식으로 Threads와 Shorts 대본 제작.
- 확정본에서 새 통찰·수정만 다시 회수.

완료 기준: 어떤 원문에서 어떤 생각이 나와 어떤 원고에 쓰였고 무엇이 새로 생겼는지 화면에서 왕복 추적 가능. 학생·제3자 정보를 보호하고 자기 콘텐츠의 순환 인용을 차단.

### 2단계: 웹 검토·편집과 중앙 저장

- yt_research UI 재사용, 공통 API와 DB 스키마 도입.
- 한 종류의 콘텐츠부터 DB를 유일한 쓰기 원본으로 전환. 전환하지 않은 종류는 기존 볼트 소유권 유지.
- Markdown은 export로 전환하고 같은 데이터를 Git·DB 양쪽에서 자유 편집하지 않는다.
- 3개 기기에서 읽기·수정·승인·충돌 처리, 권한, 백업 복원을 검증.

완료 기준: 사용자가 commit이나 frontmatter 편집 없이 작업을 이어갈 수 있다.

### 3단계: worker 이전과 코드 통합

- Python 제작/검증/발행 엔진을 공통 API에 연결. TS/Python 중복 카드 규칙은 서버 한 곳에서 관리하고 스키마 계약 테스트 추가.
- 렌더러 공통 코어 + 스타일/job 프로필로 통합. 기존 출력의 컷·자막·음량 회귀검증 후 중복 제거.
- Linux worker는 ASR·폰트 이식과 장애 재개 테스트 이후 연결.
- GitHub Actions는 테스트·배포·백업/주기 점검 위주로 축소. 이전 전까지 기존 실행자는 유지하며 동일 job에 두 실행자가 붙지 않게 한다.

완료 기준: 맥북을 끈 상태에서도 수집·제작·승인 대기·환류가 진행되고, worker 재시작 후 같은 작업이 중복 발행되지 않는다.

### 4단계: 과거 자산 회수

- 기존 SNS 폴더의 원고·템플릿·분석·사본을 구분하고 동일 원고를 dedupe한다.
- 파일 경로→안정 ID 매핑표, 원문 hash, 기존 링크를 보존한다.
- 승인된 콘텐츠부터 배치로 지식 후보를 추출하고 '기존 지식 보완'을 우선한다.
- 전체 파일을 한 번에 무검토 지식으로 승격하지 않는다.
- 백업·row 수·hash·링크 보존·역이관 검증 후 레거시 entrypoint를 폐기한다.

## 9. 정리 후 코드 경계 예시

아래는 목표 책임 분리이며 즉시 디렉터리를 옮기라는 뜻은 아니다.

```text
web/                    기존 yt_research UI를 확장
knowledge/              출처·주장·관계·승격·검색 자격
content/                브리프·채널별 원고·revision
quality/                주장 근거·개인정보·문체·검수/승인
workers/                작업 lease·재시도·실행
connectors/             Plaud·YouTube·Threads·Stibee·Telegram
media/                  ASR 어댑터·공통 렌더·편집 프로필
contracts/              API·상태·이벤트 계약
legacy/                 호출이 제거된 후 이동할 옛 진입점
```

두 저장소를 반드시 하나로 합칠 필요는 없다. 먼저 공통 API와 데이터 소유권을 확정하고, 저장소 통합은 나중에 개발 편의에 따라 결정한다.

**최우선 투자 대상은 에이전트 수나 서버 수가 아니라, 승인한 내 지식이 원고의 입력이 되고 최종 수정이 다시 지식으로 돌아오는 연결이다.**
